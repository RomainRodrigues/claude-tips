Plutôt que de décortiquer toi-même une stack trace, colle-la telle quelle à Claude Code : il lit le message, retrouve le fichier et la ligne en cause, puis propose et applique un correctif.

## Prérequis

- Claude Code installé et lancé à la racine du projet concerné.
- Un moyen de reproduire l'erreur (une commande, un test qui échoue, un `npm run dev` qui plante).
- Idéalement, un dépôt git propre (rien en attente) pour pouvoir relire le diff proposé.

## Étapes

::steps{level="3"}
### Reproduire l'erreur et copier le message complet

Lance la commande qui déclenche le bug et garde tout le message, y compris la stack trace complète — plus il y a de contexte, mieux Claude localise la cause.

```bash [Terminal]
npm test
```

### Coller l'erreur à Claude Code

Démarre une session dans le projet et colle le message d'erreur directement dans le prompt, avec la commande qui l'a déclenché.

```bash [Terminal]
claude
```

```text [Dans la session Claude Code]
je vois cette erreur quand je lance `npm test` :

TypeError: Cannot read properties of undefined (reading 'id')
    at getUserSession (src/auth/session.ts:42:18)
    at login (src/auth/login.ts:17:9)
```

### Demander des pistes avant d'appliquer le correctif

Sur un bug qui n'est pas trivial, demande d'abord des explications et plusieurs pistes plutôt qu'un correctif direct — tu gardes la main sur l'approche choisie.

```text [Dans la session Claude Code]
explique-moi pourquoi ça plante, et propose deux ou trois façons de corriger ça
```

### Laisser Claude corriger et vérifier

Une fois l'approche choisie, demande l'application du correctif puis la vérification immédiate avec la commande qui échouait au départ.

```text [Dans la session Claude Code]
applique la correction avec la vérification de null que tu proposes, puis relance npm test pour vérifier que ça passe
```

### Relire le diff avant de committer

Avant de valider quoi que ce soit, fais-toi expliquer le changement et regarde le diff.

```text [Dans la session Claude Code]
résume ce que tu as changé et pourquoi
```

```bash [Terminal]
git diff
```
::

## Résultat attendu

Claude Code te montre le fichier et la ligne fautifs, explique la cause probable, applique un correctif ciblé (pas juste un `try/catch` qui masque le symptôme), puis relance lui-même la commande qui échouait pour prouver que l'erreur a disparu.

::warning
**Corriger la cause, pas le symptôme.** Une demande vague comme *"corrige ce bug"* peut produire un correctif qui fait taire l'erreur sans régler le vrai problème. Précise que tu veux une correction de la cause racine, par exemple : *"le build échoue avec cette erreur : [erreur collée]. corrige-la et vérifie que le build passe. corrige la cause, ne masque pas juste l'erreur."*
::

## Variantes

Pour un bug reproductible par une commande précise, tu peux sauter la conversation et lancer Claude Code en mode non-interactif directement sur les logs : `cat erreur.log | claude -p "trouve et corrige la cause de cette erreur, puis relance la commande pour vérifier"`. Si le bug n'apparaît que par intermittence (race condition, flakiness), dis-le explicitement à Claude — ça l'oriente vers des causes différentes qu'un bug reproductible à 100 %.
