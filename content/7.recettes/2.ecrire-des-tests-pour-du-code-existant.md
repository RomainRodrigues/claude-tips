Un module ancien sans aucun test te fait peur dès que tu dois y toucher ? Claude Code peut lire le code existant, en déduire le comportement attendu, et écrire une suite de tests dans le style déjà utilisé ailleurs dans ton projet.

## Prérequis

- Un framework de test déjà en place dans le projet (Jest, Vitest, pytest, XCTest...) — sinon, dis à Claude d'en installer un avant de commencer.
- Le module ou fichier ciblé identifié (nom de fichier ou description de la fonctionnalité).

## Étapes

::steps{level="3"}
### Repérer le code non testé

```text [Dans la session Claude Code]
trouve les fonctions de src/services/NotificationService.ts qui ne sont couvertes par aucun test
```

### Générer un premier squelette de tests

```text [Dans la session Claude Code]
ajoute des tests pour NotificationService.ts
```

Claude Code regarde tes fichiers de test existants pour reprendre le même framework, le même style d'assertions et les mêmes conventions de nommage — tu n'as pas besoin de les préciser s'il y a déjà des exemples dans le projet.

### Compléter avec les cas limites

Une fois le squelette en place, demande explicitement les cas oubliés : erreurs, valeurs limites, entrées inattendues.

```text [Dans la session Claude Code]
ajoute des cas de test pour les conditions limites : notification sans destinataire, payload vide, envoi en double
```

### Lancer les tests et corriger les échecs

```text [Dans la session Claude Code]
lance les nouveaux tests et corrige les échecs
```

Si un test échoue parce que le code testé a un vrai bug (et pas parce que le test est mal écrit), dis-le à Claude pour qu'il corrige le bon côté.

### Vérifier la couverture obtenue

```text [Dans la session Claude Code]
relance les tests avec la couverture de code et dis-moi ce qui reste non couvert
```
::

## Résultat attendu

Un nouveau fichier de test (ou des tests ajoutés à un fichier existant) qui suit les conventions du projet, passe au vert, et couvre à la fois le chemin normal et quelques cas limites réalistes — pas seulement un test qui vérifie que la fonction ne plante pas.

::tip
**Sois précis sur ce que tu veux vérifier.** *"ajoute des tests pour foo.py"* donne un résultat correct mais générique. *"écris un test pour foo.py qui couvre le cas où l'utilisateur est déconnecté, sans mocks"* donne un résultat plus proche de ce que tu attends du premier coup.
::

## Variantes

Pour un module critique, essaie le pattern Écrivain/Relecteur avec deux sessions : une première session écrit les tests à partir du comportement attendu (avant même de regarder l'implémentation), une seconde écrit ou corrige le code pour les faire passer — une forme de TDD assistée. Pour un très gros module hérité, demande d'abord un audit (*"liste les zones les plus risquées de ce fichier à tester en priorité"*) avant de tout tester d'un coup.
