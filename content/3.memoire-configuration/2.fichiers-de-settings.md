Les fichiers de settings sont des fichiers JSON qui changent le comportement de Claude Code : le modèle de départ, ce qu'il peut faire sans demander, les fichiers qu'il ne doit pas lire, l'apparence du terminal, ou ce que ton organisation impose.

## Quand l'utiliser

Utilise un fichier de settings dès que tu veux qu'un réglage survive à la fermeture de la session : un modèle par défaut, des règles de permission, une variable d'environnement pour tout le projet. Pour un changement ponctuel, une seule session, préfère un flag en ligne de commande ou une commande comme `/model`.

## Exemple minimal

Trois familles de fichiers existent, chacune avec un usage précis :

::field-group
  :::field{name="~/.claude/settings.json" type="Utilisateur"}
  Tes préférences perso, sur **tous** tes projets : thème, modèle par défaut, tes propres règles de permission.
  :::

  :::field{name=".claude/settings.json" type="Projet partagé"}
  Réglages communs à toute l'équipe. À committer dans Git.
  :::

  :::field{name=".claude/settings.local.json" type="Projet local"}
  Tes réglages perso pour **ce projet uniquement**. Claude Code l'ajoute automatiquement à tes exclusions Git la première fois qu'il l'écrit.
  :::
::

Un fichier `settings.json` minimal, qui autorise le lint et le test sans demander, et bloque la lecture des fichiers `.env` :

```json [~/.claude/settings.json]
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run test *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}
```

La ligne `$schema` est optionnelle : elle donne l'auto-complétion et la validation dans VS Code et les éditeurs compatibles JSON Schema.

::note
Un fichier de settings est du JSON strict : pas de commentaires `//`, pas de virgule finale. Une erreur de syntaxe est signalée comme une **Settings Error** au démarrage de la session.
::

## Exemple réaliste

Un fichier d'équipe, committé à la racine du dépôt dans `.claude/settings.json`, qui fixe des permissions, envoie de la télémétrie, et enregistre un hook :

```json [.claude/settings.json]
{
  "permissions": {
    "allow": ["Bash(npm run *)"],
    "ask": ["Bash(git push *)"],
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)"
    ]
  },
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1"
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh" }
        ]
      }
    ]
  }
}
```

Chaque coéquipier peut ensuite surcharger une valeur pour lui-même dans son propre `.claude/settings.local.json`, sans toucher au fichier partagé :

```json [.claude/settings.local.json]
{
  "model": "claude-opus-4-8"
}
```

Après avoir modifié un fichier, vérifie ce qui a été chargé :

```text [Dans une session Claude Code]
/status
```

La ligne **Setting sources** liste chaque fichier de settings pris en compte pour la session en cours.

## Ordre de priorité

Quand la même clé est définie à plusieurs endroits, Claude Code utilise la valeur du niveau le plus haut. Du plus fort au plus faible :

| Niveau | Source | Qui l'applique |
| :--- | :--- | :--- |
| 1 | **Settings managés** — `managed-settings.json`, MDM, ou la console claude.ai | Ton organisation |
| 2 | **Ligne de commande** — `claude --settings` | Toi, pour cette session |
| 3 | **Projet local** — `.claude/settings.local.json` | Toi, sur ce projet |
| 4 | **Projet partagé** — `.claude/settings.json` | Toute l'équipe du projet |
| 5 | **Utilisateur** — `~/.claude/settings.json` | Toi, sur tous les projets |

::tip
Les listes (comme `permissions.allow`) ne s'écrasent pas entre fichiers : elles **fusionnent**. Chaque fichier peut ajouter des règles sans supprimer celles d'un autre niveau. Quelques clés font exception à cette fusion, comme `fallbackModel` ou `availableModels` — voir la doc officielle pour le détail.
::

## Pièges fréquents

::warning
**Une valeur que tu as réglée est ignorée.** La cause la plus fréquente : un niveau plus haut définit la même clé (settings managés, `--settings`, ou une variable d'environnement qui prend le dessus sur certaines clés comme `model`). Lance `/status` pour voir quels fichiers sont chargés, et `claude doctor` pour voir les entrées rejetées.
::

::caution
**Une règle `permissions.allow` dans un fichier de projet ne s'applique pas tant que tu n'as pas fait confiance au dossier.** Les règles `allow` et `additionalDirectories` d'un `.claude/settings.json` partagé attendent que chaque personne valide la confiance au projet (« workspace trust »). Les règles `deny` et `ask`, elles, s'appliquent immédiatement, avec ou sans confiance.
::

::note
**Claude Code recharge les fichiers de settings automatiquement** pendant que la session tourne — inutile de relancer Claude Code après une modification de `permissions` ou `hooks`. Certaines clés, comme `model`, ne sont lues qu'au démarrage : utilise `/model` pour changer de modèle en cours de session plutôt que d'éditer le fichier.
::
