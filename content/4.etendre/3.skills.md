Une skill est un ensemble d'instructions — et éventuellement de scripts ou de fichiers de référence — rangé dans un dossier : Claude peut la charger automatiquement quand c'est pertinent, ou tu peux l'invoquer toi-même avec `/nom-de-la-skill`. Contrairement à `CLAUDE.md`, son contenu ne consomme du contexte que lorsqu'elle est réellement utilisée.

::note
Les [commandes personnalisées](/etendre/commandes-personnalisees) sont en réalité des skills à un seul fichier. Cette page va plus loin : fichiers de support multiples, exécution isolée dans un subagent, contrôle fin de qui peut invoquer quoi.
::

## Quand l'utiliser

Dès que tu te surprends à copier-coller les mêmes instructions, listes de contrôle ou procédures multi-étapes dans le chat. Une skill est aussi le bon outil quand la procédure a besoin de documentation de référence volumineuse (que Claude ne doit lire que si nécessaire) ou de scripts exécutables plutôt que de simples instructions en langage naturel.

## Exemple minimal

Une skill un peu plus riche qu'une simple commande : plusieurs fichiers, dont un chargé seulement à la demande.

```text [Arborescence]
.claude/skills/review-pr/
├── SKILL.md
└── checklist.md
```

```markdown [.claude/skills/review-pr/SKILL.md]
---
description: Relit une pull request avec la checklist de l'équipe. Utile quand on demande de relire une PR ou un diff.
---

Relis les changements en suivant la checklist de l'équipe.

Pour la liste complète des points à vérifier, voir [checklist.md](checklist.md).
```

Claude ne charge `checklist.md` que s'il en a besoin pour répondre — garder `SKILL.md` court et déporter le détail dans des fichiers séparés est la pratique recommandée dès qu'une skill dépasse quelques instructions simples.

## Exemple réaliste

Une skill complète pour relire une pull request GitHub : elle s'exécute dans un subagent isolé (`context: fork`), pré-autorise uniquement les commandes `gh pr`, prend le numéro de PR en argument, et récupère elle-même le diff et les commentaires avant de répondre.

```yaml [.claude/skills/review-pr/SKILL.md]
---
name: review-pr
description: Relit une pull request GitHub en profondeur
context: fork
agent: Explore
allowed-tools: Bash(gh pr *)
disable-model-invocation: true
argument-hint: [numero-pr]
---

## Revue de PR GitHub

Relis la PR GitHub #$0 :

1. Lis le diff : !`gh pr diff $0`
2. Vérifie les fichiers modifiés : !`gh pr diff $0 --name-only`
3. Relis les commentaires existants : !`gh pr view $0 --comments`
4. Résume les changements
5. Signale les problèmes potentiels
6. Propose des améliorations

Réponds avec : un résumé (2-3 phrases), les fichiers concernés, les risques identifiés, des suggestions, et une recommandation finale (approuver / demander des changements).
```

Invocation :

```text [Dans la session Claude Code]
/review-pr 42
```

`context: fork` isole cette skill dans un subagent dédié : elle ne voit pas l'historique de ta conversation en cours, et tourne par défaut en arrière-plan pendant que tu continues à travailler.

## Pièges fréquents

::warning
**Garde `SKILL.md` en dessous de 500 lignes.** Au-delà, déporte le matériel détaillé dans des fichiers séparés (`reference.md`, `examples.md`...) référencés depuis `SKILL.md` — ils ne seront chargés que si Claude en a réellement besoin.
::

::warning
**`disable-model-invocation` et `user-invocable` ne font pas la même chose.** `disable-model-invocation: true` t'autorise à invoquer la skill toi-même, mais empêche Claude de la déclencher automatiquement (utile pour un déploiement ou un commit, qui ont un effet de bord réel). `user-invocable: false` fait l'inverse : la skill disparaît du menu `/`, seul Claude peut l'invoquer (utile pour des connaissances de fond).
::

::caution
**Une skill en `context: fork` en arrière-plan contourne les checkpoints.** Les modifications faites par un subagent lancé en arrière-plan ne sont pas annulées par `/rewind` — si tu dois revenir en arrière, utilise Git.
::

::note
**Le contenu complet d'une skill reste dans le contexte après son invocation**, tour après tour, et coûte donc des tokens à chaque échange tant que la conversation continue. `allowed-tools`, en revanche, ne s'applique qu'au tour où la skill est invoquée : la permission s'efface dès ton message suivant.
::
