Un workflow, ici, c'est simplement une façon de formuler ta demande à Claude qui fonctionne bien pour un type de tâche récurrent : comprendre un code inconnu, corriger un bug, refactorer, écrire des tests.

## Quand l'utiliser

Ces recettes sont un point de départ à adapter à ton projet — elles marchent dans n'importe quelle interface de Claude Code (terminal, VS Code...). Utilise-les surtout quand tu ne sais pas trop comment formuler ta demande.

## Exemple minimal

Pour découvrir un nouveau projet, la première question à poser :

```text [Dans la session Claude Code]
donne-moi un aperçu général de ce projet
```

Puis affine avec des questions plus précises une fois la vue d'ensemble en tête.

## Exemple réaliste

Quatre workflows du quotidien, avec la progression de questions qui fonctionne bien pour chacun.

::steps{level="3"}
### Comprendre un code inconnu

```text [Dans la session Claude Code]
donne-moi un aperçu général de ce projet
```

```text [Dans la session Claude Code]
explique les patterns d'architecture principaux utilisés ici
```

```text [Dans la session Claude Code]
trouve les fichiers qui gèrent l'authentification des utilisateurs
```

Commence large, puis rétrécis vers ce qui t'intéresse. Utilise le vocabulaire métier du projet pour de meilleurs résultats.

### Corriger un bug efficacement

```text [Dans la session Claude Code]
je vois une erreur quand je lance npm test : [colle l'erreur ici]
```

```text [Dans la session Claude Code]
propose plusieurs façons de corriger le @ts-ignore dans user.ts
```

```text [Dans la session Claude Code]
applique la correction que tu as suggérée
```

Donne à Claude la commande pour reproduire le problème et la stack trace complète — ça évite un aller-retour.

### Refactorer du code

```text [Dans la session Claude Code]
trouve les usages d'API dépréciées dans notre code
```

```text [Dans la session Claude Code]
propose comment refactorer utils.js pour utiliser des fonctionnalités JavaScript modernes
```

```text [Dans la session Claude Code]
refactorise utils.js avec ces fonctionnalités, en gardant le même comportement, puis lance les tests
```

Fais les refactors par petits incréments testables plutôt qu'en un seul gros changement.

### Écrire des tests

```text [Dans la session Claude Code]
trouve les fonctions de NotificationsService qui ne sont pas couvertes par des tests
```

```text [Dans la session Claude Code]
ajoute des tests pour le service de notifications, y compris les cas limites
```

```text [Dans la session Claude Code]
lance les nouveaux tests et corrige les échecs
```

Claude examine tes fichiers de tests existants pour reprendre le même style, framework et conventions d'assertions.
::

## Pièges fréquents

::tip
**Utilise `@` pour référencer un fichier ou un dossier** au lieu de décrire où se trouve le code : `explique la logique dans @src/utils/auth.js`. Claude lit le fichier avant de répondre, ce qui évite un aller-retour de recherche.
::

::note
**Pour une exploration qui va lire beaucoup de fichiers, délègue à un subagent** plutôt que de laisser Claude tout lire dans ta conversation principale : `utilise des subagents pour investiguer comment notre système d'authentification gère le refresh de token`. Seul le résumé final revient dans ton contexte.
::

::warning
**Avant d'éditer, passe en mode plan pour les changements ambitieux ou incertains** (`Shift+Tab` jusqu'à `⏸ plan mode on`, ou `claude --permission-mode plan`). Claude explore et propose un plan sans toucher au code tant que tu ne l'as pas validé — utile quand la portée du changement touche plusieurs fichiers ou que tu ne connais pas bien le code concerné. Pour un changement trivial et bien cerné, ce détour ajoute juste de la friction.
::

::caution
**Pour du travail non-interactif (CI, scripts, hooks), utilise `claude -p` plutôt que le mode interactif.** Exemple : `git log --oneline -20 | claude -p "résume ces commits récents"`. Le comportement des permissions et des sorties diffère du mode interactif — voir la documentation dédiée au mode non-interactif pour le détail.
::
