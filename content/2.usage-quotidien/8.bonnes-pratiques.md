Claude Code n'est pas un chatbot qui répond et attend : il lit tes fichiers, lance des commandes, fait des changements, et travaille de façon autonome pendant que tu observes, corriges, ou t'absentes. Ça change la façon de collaborer avec lui.

## Quand l'utiliser

Ces pratiques s'appliquent à toutes les sessions, mais elles comptent d'autant plus que la tâche est longue, ambiguë, ou que tu comptes laisser Claude travailler sans surveillance constante.

::note
La contrainte de fond derrière la plupart de ces conseils : la fenêtre de contexte de Claude se remplit vite, et ses performances se dégradent quand elle est pleine. Voir la page dédiée à la gestion du contexte.
::

## Exemple minimal

Le réflexe le plus rentable : donner à Claude un moyen de vérifier lui-même son travail.

```text [Dans la session Claude Code]
écris une fonction validateEmail. Exemples de cas de test :
user@example.com → true, invalide → false, user@.com → false.
lance les tests une fois l'implémentation faite
```

Sans ce genre de critère vérifiable, « ça a l'air fini » est le seul signal disponible — et c'est toi qui dois repérer chaque erreur.

## Exemple réaliste

Le déroulé recommandé pour une fonctionnalité un peu ambitieuse : explorer, planifier, coder, valider.

::steps{level="3"}
### Explorer en mode plan

```bash [Terminal]
claude --permission-mode plan
```

```text [Dans la session Claude Code]
lis /src/auth et comprends comment on gère les sessions et la connexion
```

Claude lit les fichiers et répond à tes questions sans rien modifier.

### Construire un plan

```text [Dans la session Claude Code]
je veux ajouter l'authentification Google OAuth. Quels fichiers changent ?
quel est le flux de session ? fais un plan
```

`Ctrl+G` ouvre le plan dans ton éditeur de texte pour le modifier directement avant que Claude ne continue.

### Implémenter avec vérification

```text [Dans la session Claude Code]
implémente le flux OAuth de ton plan. écris des tests pour le
callback handler, lance la suite de tests et corrige les échecs
```

### Committer

```text [Dans la session Claude Code]
commit avec un message descriptif et ouvre une PR
```
::

Quelques réflexes complémentaires qui font une vraie différence sur la durée :

::steps{level="3"}
### Écris un CLAUDE.md concis

Lance `/init` pour générer un `CLAUDE.md` de départ. N'y mets que ce que Claude ne peut pas deviner en lisant le code : commandes de build, conventions de style qui diffèrent des standards, gotchas non évidents. Un fichier trop long noie les instructions importantes.

### Corrige tôt, corrige souvent

Interromps Claude dès que tu le vois partir dans la mauvaise direction (`Escape`), plutôt que de le laisser continuer. Si tu as corrigé la même chose deux fois dans la même session sans succès, le contexte est probablement pollué par les tentatives ratées : `/clear` et reformule un prompt plus précis qui intègre ce que tu as appris.

### Délègue la recherche à des subagents

Une exploration qui lit beaucoup de fichiers remplit ton contexte principal. Demande explicitement `utilise un subagent pour investiguer...` : la recherche se fait dans une fenêtre de contexte séparée, et seul le résumé revient.

### Ajoute une étape de relecture indépendante

Avant de considérer une tâche terminée, demande une relecture dans un contexte neuf : `utilise un subagent pour relire le diff par rapport à PLAN.md`. Un relecteur qui ne voit que le diff, sans le raisonnement qui l'a produit, repère des choses qu'on rate soi-même.
::

## Pièges fréquents

::warning
**La « session fourre-tout ».** Tu commences une tâche, puis tu demandes autre chose sans rapport, puis tu reviens à la première — le contexte se remplit d'informations non pertinentes qui perturbent Claude. Utilise `/clear` entre deux tâches sans lien.
::

::caution
**Les corrections répétées sans succès.** Claude se trompe, tu corriges, ça reste faux, tu corriges encore — le contexte accumule des tentatives ratées qui polluent les réponses suivantes. Après deux corrections infructueuses sur le même point, `/clear` et repars avec un prompt plus précis plutôt que de t'acharner.
::

::warning
**Le CLAUDE.md surchargé.** Si Claude ignore la moitié de tes instructions, ton `CLAUDE.md` est probablement trop long : les règles importantes se noient dans le bruit. Élague sans pitié — si Claude fait déjà quelque chose correctement sans l'instruction, supprime-la.
::

::note
**Faire confiance sans vérifier.** Une implémentation qui a l'air correcte peut rater des cas limites. Fournis toujours un moyen de vérifier (tests, script, capture d'écran à comparer) — sans ça, ne considère pas le travail comme livrable.
::
